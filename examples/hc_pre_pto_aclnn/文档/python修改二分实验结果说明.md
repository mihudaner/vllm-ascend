# HC_pre：从 Python 生成二分累加的验证

本文保留关键结果。完整输入、算子包和原始采集留在本地实验归档，未上传；下文标注“本地归档”的材料不提供仓内链接。

本次直接修改 `hc_pre.py`，由 PyPTO/PTOAS 生成 C++，再接入原 ACLNN 工程。旧版手写 C++ 实验保留在相邻目录，本文只记录本次 Python 版本，结果不混用。

**结论：Python 二分版有局部性能收益，但不能保证精度更好。** 普通/随机 134 例两版全部通过；24 个超差全部来自人为构造的非随机相消用例，不是实际模型运行中发现的异常样本。按 FP32 golden 门槛，原版通过更多；对照 FP64 高精度参考，这 24 例中原版更准 12 例、二分更准 12 例。T97～144 的 7 个测点在两组 ABBA、四个配对中都更快，缩短 1.63～3.34 μs（5.82%～11.16%）。其他档收益较小，T32/T49/T64 未确认提升。

## 1. 改了哪里

只改第二阶段跨 K 段的求和：Sinkhorn 分支、门控/混合分支各有一次投影 partial 求和、一次 RMS partial 求和。共四处 Python 调用，展开到六档后共 24 处。

```python
# 原版：按行顺序累加各 K 段的部分和。
total = pl.col_sum(parts)

# 修改版：显式提供临时 tile，选择库的二分归约。
# 临时 UB 的地址与复用由编译器分配。
tmp = pl.create_tile([LINEAR_OK, T_TILE * MIX_PAD], dtype=pl.FP32)
total = pl.col_sum(parts, tmp)
```

RMS 同样修改，临时 tile 的形状为 `[RMS_OK, T_TILE]`。K 段内平方和、Cube 投影、Sinkhorn 每轮归一化及四路混合的加法不在本次修改范围内。

## 2. Python 如何对应 C++

两版均使用同一套 PyPTO、PTOAS、PTO ISA 编译；六档的入口参数未变化，ACLNN 的封装与 workspace 计算未修改。重新生成的原版 C++ 与仓内原版除注释外完全一致。

以 T96 为例，编译后为：

```cpp
// 原版
TCOLSUM(dst, src);

// 修改版；true 由 Python 传入 tmp 自动生成。
TCOLSUM(dst, src, tmp, true);
```

T96 修改版 C++ 的四处调用位于 894、994、2089、2189 行，分别对应 Python 的 400、405、661、666 行。

原版生成 C++（本地归档） · [修改版生成 C++](../generated/hc_exact96.cpp) · [修改版 PTO](../generated/hc_exact96.pto)

8 段投影的二分过程：先加相邻两段，得到 4 行；再合成 2 行，最后合成 1 行。各层结果写进临时 tile，最终复制到输出。遇到奇数行时，库会把最后一行加到本层第一组结果中。

这与旧版手写 C++ 的“原地保留隔行结果、奇数尾项留到下一层”不是同一实现。缓冲、指令排布可能不同，奇数段的浮点加法顺序也不同，所以需要重测。

## 3. 验证方法

复用上次输入与 golden：281 个精度用例，其中普通/随机 134 个、构造相消 147 个。主参考仍是原 FP32 golden，补充 FP64 误差对照；构造用例不通过 FP32 门槛，不自动等于数学结果更差。

性能覆盖 27 个 T（1～500 的代表值及分档边界），不启用 replay。每次预热 5 次、正式 20 次，执行两组 ABBA，共每版每个 T 80 个正式样本。使用 `msprof` 的算子设备耗时，报告中位数及两组趋势。

## 4. 精度结果

**下表的“通过”是满足原 CPU PyTorch FP32 golden 的容差，不是与无限精度数学真值完全一致。** golden 实现（本地归档）对完整 K 轴调用一次 `torch.matmul`，内部加法顺序由 CPU 矩阵乘实现决定；它没有照抄 PTO 的分段顺序累加，也没有指定本次二分顺序。

| 用例 | 原版通过 | Python 二分版通过 |
|---|---:|---:|
| 普通/随机 | 134/134 | 134/134 |
| 构造相消 | 147/147 | 123/147 |
| 合计 | 281/281 | 257/281 |

“通过”沿用原测试门槛：逐元素误差超过 `0.005 + 0.005 × abs(golden)` 记为超差，mixed/post 超差比例不超过 0.5%，comb 不超过 2%。24 个差异全部出现在构造用例的 post；没有普通输入失败，也没有设备执行错误。

**这 24 例全部是专门构造的非随机极端相消用例。** 测试刻意安排正负较大数与小量的位置，并通过门控 scale 放大舍入差异，检查不同加法顺序是否丢失小量。它们不是普通随机样本，也不是实际模型运行中发现的异常；不能把 24/147 当作实际模型输入的失败率。

因此，这张表支持“在本批用例、当前 FP32 golden 门槛下，原版更容易通过”，但不代表原版的加法顺序与 golden 相同，也不代表原版在数学上总是更准。普通/随机 134 例两版都通过，只说明都在容差内，不代表误差相同。

为区分“偏离 golden”和“离数学结果更远”，另用相同输入的 FP64 计算作辅助参考。这 24 例按 post 的平均绝对误差比较：

| 相对 FP64 高精度参考 | 用例数 |
|---|---:|
| 原版更接近，二分误差更大 | 12 |
| 二分更接近，但偏离了 FP32 golden | 12 |

这里的“更准”指更接近 FP64 参考。FP64 本身仍有舍入，不是无限精度的数学真值；它用于辅助判断这批 FP32 相消用例的舍入差异，**没有替换上表判定通过率的 FP32 golden**。

## 6. 为什么与旧版结果不同，性能原因确认到哪

**已确认的实现差异：** Python 路径使用库的临时 tile，逐层把结果压紧到前半部分；旧手写 C++ 在原输入中隔行留下结果。11 段时两者的加法分组也不同。本次与旧实验输出比较，8/16 段测点逐字节一致，11 段测点出现差异，因此不能复用旧精度结论。

**能从源码确认的机制：** 8 段求和仍需 7 次向量加法，二分把连续依赖缩为 3 层，而不是少做了加法。库的顺序路径在每次相加后等待 Vector 完成；二分路径先发出同一层的独立相加，再等待下一层。临时 tile 和相应地址安排也发生了变化。

**尚未单独证明的部分：** 本轮测到了完整算子的收益，没有重新采集归约区间的核内流水，不能断言 T97～144 节省的全部时间都来自减少等待，也不能把差别归因为某个 UB bank 冲突。当前结论是“这份 Python 生成实现有稳定的局部收益”，不是“二分在所有档都更快”。

### 本轮结论与接入决定

**综合两轮结果，采用当前全档二分实现，同步更新 Python 与六档生成核；保留以下性能和精度限制。**

- 27 个测点中，23 个中位数变快、1 个持平、3 个变慢；这不能直接等同于多数分档有稳定明显收益。
- T97～144 两组均有收益，节省 0.64～2.31 μs。T140/T144 的收益最明确，分别为 7.53%/8.24%，四个配对均更快；T100～128 为 4.04%～5.11%，各有三个配对更快；T97 仅两对更快。
- 此分档之外，变快的测点最多节省 0.64 μs，而且都只有两对更快、两对更慢。本轮仍存在执行间状态波动，不足以确认明显的全档收益。
- T32 本轮从 23.36 μs 增至 24.35 μs，中位数回退 4.24%，均值也回退 3.47%；配对之间仍有波动，不能只把它当作已排除的噪声。

精度结论与上一轮一致：普通/随机 134 例均通过；24 个构造相消差异按 FP64 对照各有 12 例原版/二分更准。接入的是本轮实际验证的生成文件；C++ 原样复制，PTO 只将源码定位路径改为仓内相对路径。接口与 workspace 计算未变化，未重新验证 Torch、SK 或 Early-Start。
