# HC_pre 跨 K 分段二分累加：精度与性能对照

本文保留关键结果。完整输入、算子包和原始采集留在本地实验归档，未上传；下文标注“本地归档”的材料不提供仓内链接。

## 1. 结论

> 范围纠正：本文记录手写 C++ 原地二分实验，不是从 Python `hc_pre.py` 修改后编译生成的版本。用户要求以 Python 修改为准，因此该实验不作为 Python 二分方案的性能结论；已撤回同步到 Git 工作区的手写 C++ 改动。后续验证必须从 Python 生成两版代码。

**以下结论仅适用于这次手写 C++ 实验。**

- **精度**：134 个常规及随机用例，两版全部通过原测试标准，误差整体接近。二分对部分输入更准，对另一些输入更差。
- **大数抵消**：144 个构造用例中，相对 FP64，二分 10 例变好、10 例变差、124 例相同；没有减少丢失小量的用例总数。
- **验收差异**：原 FP32 golden 下，原版 281/281 通过，二分 261/281 通过。20 个不通过均是构造用例的 post 超差，其中 10 个实际上更接近 FP64，不能把“不符合 golden”全部理解成“数学上更差”。
- **性能**：27 个 T，覆盖六档及原有常规 B/S 对应的 T，最大到 500。24 档的合并中位数略慢；另外 3 档略快，但两组复测方向相反。没有任何一档在两组中都获得正收益。

手写 C++ 候选只保留在本文的实验副本中，Git 工作区已撤回这组改动；未提交、未推送。

## 2. 改的是什么

基线为 `hc_pre_aclnn` 的 `0213715f`。此处生成核、kernel 入口和 workspace 配置与 `213829bfb` 一致。

只改最后汇总 K 分段的加法：**投影 partial 和 RMS 平方和 partial 都改**，Sinkhorn/post 路径及 mixed 路径各两处，六个生成核共 24 处。分段内部的 Cube 累加、Sinkhorn 自身的行列归一化、四路 mixed 加权求和均保持原实现。

```text
顺序：(((((((p0+p1)+p2)+p3)+p4)+p5)+p6)+p7)

二分：第一层  a0=p0+p1  a1=p2+p3  a2=p4+p5  a3=p6+p7
      第二层  b0=a0+a1  b1=a2+a3
      第三层  total=b0+b1
```

最终实现直接复用已读入的 partial UB，层级和偏移在编译期展开，不增加 UB/GM 缓冲。11 段时未配对的尾段保留到下一层；16 段需要四层。源 partial 在该次归约后不再使用，因此允许原地覆盖。GM 中的 partial 不修改。

| T 范围 | 投影段数 | RMS 段数 | 修改范围 |
|---|---:|---:|---|
| 1～32 | 11 | 11 | 两种 partial、两条消费路径 |
| 33～48 | 16 | 16 | 同上 |
| 49～95 | 8 | 8 | 同上 |
| 96 | 8 | 16 | 同上 |
| 97～144 | 8 | 8 | 同上 |
| >144 | 8 | 8 | 同上 |

实际验证的是 **ACLNN 工程的 C++ 生成核最小改动**，未重新生成整个 Python 算子。原 Python 中对应四处 `pl.col_sum(c_parts/c_sq/m_parts/m_sq)`。本次 `.pto` 文件保留基线内容作为来源记录，不代表修改后的 C++ IR。

### 2.2 新辅助函数实际怎么加

原版的两参数 `TCOLSUM` 使用库中的 `SequentialSum`：每次把下一行加到结果行，每次加法后放一个 Vector 屏障。新版直接在源 tile 的行上做下列操作，最后把第 0 行作为结果：

```cpp
// 展示 8 行时展开后的逻辑；p[i] 表示 UB 中第 i 行向量。
// 第一层：四次 vadd，各自处理不同的两行。
p[0] += p[1]; p[2] += p[3]; p[4] += p[5]; p[6] += p[7];
pipe_barrier(PIPE_V);
// 第二层：两次 vadd。
p[0] += p[2]; p[4] += p[6];
pipe_barrier(PIPE_V);
// 第三层：一次 vadd。
p[0] += p[4];
pipe_barrier(PIPE_V);
```

实际代码中的 `Step=1/2/4/...` 对应层级，`Row` 对应本层的起始行，`Src::RowStride` 把行号换成 UB 地址偏移。模板递归在编译期展开，不是设备运行时递归，也不会新增 kernel 派发。

这里处理的都是已经补齐有效行的 FP32 partial tile；允许覆盖这些临时 UB 行，不覆盖 GM partial。它是针对这 24 个调用点的实现，不应直接当作通用 `TCOLSUM` 替换。

代码入口：实验副本二分实现（本地归档）、入口新增 include（本地归档）、完整补丁（本地归档）。

历史差异见 cpp_change.patch（本地归档）；不再作为当前工作区改动。

## 3. 怎样验证

沿用此前的 C++ ACLNN 直接调用方式，不开 replay，不开 PTO profiler。真机为 Ascend 910_9392，本次正式比较均在物理设备 9；两版使用同一套输入文件、编译器、PTO-ISA 和运行时。

- **精度**：沿用此前 281 组输入，包含 134 个常规/随机用例、144 个抵消用例、3 个原先的小量丢失示例。包括原始 FP32 权重、先转 BF16 再升回 FP32 的权重和较大数值范围。
- **原判据**：CPU PyTorch FP32 golden；逐元素 `abs(a-g) > 0.005 + 0.005*abs(g)` 计为超差，mixed/post 允许比例 0.5%，comb 允许 2%。
- **数学误差**：另外使用相同输入数值的 CPU FP64 forward 作为参考；mixed 最后仍转换为 BF16。它用于判断谁更接近高精度结果，不替代原验收标准。
- **性能**：每轮每个 T 预热 5 次、统计 20 次。两组 ABBA：每组按“原版→二分→二分→原版”运行。每版每个 T 共 80 个有效样本；取 `msprof op_summary` 的设备 `Task Duration`，排除 Host 分配、数据拷贝等耗时。
- **控制变量检查**：T24/40/80/96/128/168 的投影和 RMS partial 有效区域逐字节一致；编译期展开与运行时循环版的 843 份输出逐字节一致。重新构建的原版 843 份输出也与前次原版记录一致。

T100/120/140 是同设备、同配置单独补测的三档，每档同样完成两组 ABBA，没有混用旧性能数据。

## 4. 精度：总体接近，不是普遍变准

### 4.1 原测试标准下，哪些通过、哪些不通过

| 用例类型 | 用例数 | 原版通过 | 二分通过 |
|---|---:|---:|---:|
| 常规及随机输入 | 134 | 134 | 134 |
| 人为构造的正负抵消输入 | 144 | 144 | 124 |
| 原先的小量丢失示例 | 3 | 3 | 3 |
| **合计** | **281** | **281** | **261** |

**“不通过”指输出与原 FP32 golden 的差距超过验收阈值，不是运行报错。** 20 个用例均是 post 超差，mixed 和 comb 仍通过。测试既检查单个元素的误差，也检查超差元素占比：

```text
单个元素允许误差 = 0.005 + 0.005 × abs(golden)
post 超差元素占比超过 0.5%，该用例判为不通过。
```

这些构造用例的 golden 在 1 附近，单个元素允许误差约 0.01；二分与 golden 的差距约 0.0624，且 post 的全部元素超差，因此不通过。

但 FP32 golden 自身也会舍入。用 FP64 再核对这 20 个用例，得到两种相反的情况：

| 用例数 | 原版与 FP32 golden 的 post | 二分 post | FP64 参考 | 如何理解 |
|---|---:|---:|---:|---|
| 10 | 1.0000 | 约 1.0624 | 约 1.0624 | 原版与 golden 丢了小量；二分更准，却未通过原标准 |
| 10 | 约 1.0624 | 1.0000 | 约 1.0624 | 原版保住了小量；二分丢失小量，误差确实变大 |

因此，**不能把 20 例全部归为二分算错，也不能因为其中 10 例更准就忽略另外 10 例变差。** 原版构造用例全部通过，也只表示与 FP32 golden 一致，不代表它保住了所有数学上的小量。

### 4.2 常规及随机输入的误差有多大

以下为 134 个常规/随机用例相对 FP64 的平均绝对误差，按输出元素数汇总。“更准/更差/相同”按每个用例自身的平均绝对误差比较。

| 输出 | 原版平均误差 | 二分平均误差 | 二分更准 / 更差 / 相同 |
|---|---:|---:|---|
| mixed | 5.020024e-07 | 5.106656e-07 | 54 / 68 / 12 |
| post | 1.803270e-07 | 1.801065e-07 | 81 / 49 / 4 |
| comb | 4.614176e-08 | 4.611335e-08 | 67 / 67 / 0 |

例如 post 的二分胜出用例更多，但总体平均误差只降低约 **0.12%**；mixed 则略增。没有足够证据把它称为有实际意义的精度提升。

### 4.3 为什么改顺序会有好有坏

以 T96 为例，令 `e=2^-25`，八段中仅第 0、4、6 段非零：

| partial 排列 | 顺序结果 | 二分结果 | 数学结果 |
|---|---|---|---|
| `[e,0,0,0,1,0,-1,0]` | 0 | e | e |
| `[1,0,0,0,-1,0,e,0]` | e | 0 | e |

第一行二分先把 `1 + (-1)` 抵消，保住 e；第二行二分先算 `-1 + e`，e 被舍入丢掉。真机输出 post 对应为 `1` 或约 `1.0624187`，与这个解释一致。

先前 `16777216、1、-16777216` 的 T96 示例，两种顺序仍都会丢失 1。

## 6. 性能为什么没有提升，变慢原因定位到哪了

**目前没有定位清楚整体略慢的直接原因。** 已确认的是这版实现没有稳定收益；不能把“加法次数没减少”当作已经证明的变慢原因。

### 6.1 代码确实改变了什么

| 项目 | 原顺序累加 | 本次原地二分 |
|---|---|---|
| 8 / 11 / 16 段的向量加法次数 | 7 / 10 / 15 | 7 / 10 / 15，未减少 |
| 最长加法依赖链 | 7 / 10 / 15 层 | 3 / 4 / 4 层 |
| 归约循环内部的 Vector 屏障 | 每次加法后一次 | 每层结束后一次 |
| 加法结果写到哪里 | 反复写同一结果行 | 先写第 0、2、4、6…行，再逐层合到第 0 行 |
| 额外申请的 UB/GM 缓冲 | 无 | 无 |

表中的屏障是源码归约部分的数量，不包含共同的加载、拷贝和收尾同步，也不等于实际节省的时间。

这些 `vadd` 仍在同一个 AIV 的 Vector 流水上执行。二分不会自动把七次加法分给七个核；它只是减少前后操作的依赖，是否缩短执行间隔要看实际流水。因此，“依赖从七层降到三层”不能直接换算成整算子提速。

### 6.2 已排除什么，还缺什么证据

| 判断 | 现有证据 |
|---|---|
| 不是最终候选把前段数值算变了 | 六档投影/RMS partial 有效区域逐字节一致 |
| 不是新增 workspace 或显式临时 tile 的分配开销 | 最终候选原地归约，配置和申请量未改 |
| 不能只归因于新增运行时循环 | 已换成编译期展开版本，仍未取得稳定收益 |
| 不能据此说归约本身变慢了 | 尚未单独测量归约区间，现有数据是整算子设备耗时 |
| 不能把 UB 地址变化直接认定为原因 | 确实改变了写入行位置，但还没有流水证据证明它造成额外等待 |

要解释多出来的时间，下一步需要对照**这两个最终二进制**的归约区间指令和流水，确认是归约段自身、前后等待，还是整核排布发生变化。当前没有这份区间对照，结论保留到这里，不用猜测补齐因果。

所以目前建议保留原版：这次特定的 C++ 原地二分实现没有稳定的整体性能优势，也没有明显降低端到端误差。**这个结果不能推广成“所有二分写法都更慢”，也不是对重新生成的 Python PTO 二分版本的测试结论。**

中间尝试只保留简要记录：新增临时区的候选曾出现越界或前段 partial 异常，未纳入比较；后者原因未定界。无新增缓冲的原地版本通过了前段一致性检查。运行时双层循环版整体略慢，最终已改成编译期展开，避免用循环开销误判二分。详见 尝试摘要（本地归档），不保留这些失败版本的整套流水产物。
