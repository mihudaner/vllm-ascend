## 2. 本次要验证什么

Native 源码已核对一致：SE 报告与本次构建记录均为 `cann-recipes-infer@4c3d1e1258053c4d810322198a7fd1722c89897e`，接口为 `custom::npu_hc_pre`。两侧沿用第 2 层 attn 权重、同一组 B/S 与 seed=20261009+B×100+S。源码一致不等于编译产物或运行状态完全一致，差异会在新表中单列。

- 六档都接入 ACLNN/Torch，覆盖上表全部 14 个 B/S 场景。
- 两侧使用相同输入和权重，检查普通调用、图重放和更新输入。
- 设备 kernel 耗时与完整图重放耗时分开记录，不能拿两种口径直接比较。
- 精度阈值沿用 SE benchmark；与 CPU 参考及 Native 的比较分别列出，不把它当作官方验收标准。

## 4. 复现与原始数据

- 执行方式和依赖：[README](README.md)；接入逻辑：[Torch 接入记录](TORCH接入记录.md)。
- 权重：DeepSeek-V4-Flash-0731-w8a8，第 2 层 attn 的 fn/scale/base，报告记录每份权重 SHA256。
- 输入：BF16，seed=20261009+B×100+S，与 SE 十四场景设置相同。
- SE 历史采集与本次并非同一次运行，编译环境、设备状态差异仍可能影响耗时。
- 左侧旧 ACLNN/Native 报告：`output/all14_final/report.json`；同目录各场景保存 Native/PTO 设备 trace。
- Torch / torch_npu：`2.10.0+cpu` / `2.10.0.post2`。
- 已记录 14/14 个场景；只有上表已填入设备耗时的场景完成性能采集。
- 左侧旧 ACLNN/Native 数据的物理设备：`8`。 右侧复测三组均为设备 `0`。

### 复测观察

- T96：原版 L1 为 28.72 μs，ACLNN 为 29.40 μs；T168：分别为 38.96 / 36.32 μs。不同场景的差值有正有负，未体现出固定的接入开销。
- 原版与 ACLNN/Native 是同卡先后运行，仍存在运行时状态与计时边界差异；这轮结果尚不能拆出纯包装开销。
- PTO 对 Native、PTO 对 CPU、图重放一致性均通过 14/14。修改输入为原输入的 -0.5 倍后，Native 对 CPU 的 comb 在 B8/S5、B20/S6、B24/S5 未通过当前严格阈值；旧轮与复测相同。对应最大绝对误差为 1.985e-5、3.153e-5、1.436e-5，已补入验证表，不能把全部检查概括为全通过。
