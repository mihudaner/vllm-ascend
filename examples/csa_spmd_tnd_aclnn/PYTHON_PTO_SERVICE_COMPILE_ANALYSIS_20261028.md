## 6. 编译慢的原因

### 6.1 单套融合核编译成本较高

每套生成数 MiB 的 IR 和融合 C++，还需准备 AIC、AIV 及调度二进制。
观察到 IR 生成之后仍需约两分钟。大量磁盘文件主要是结果，
没有证据说明约 823 MiB 的落盘本身是主要瓶颈。
未做 CPU、内存、I/O profiling，不能进一步量化编译器内部热点。

### 6.2 16 个进程分别编译，未观察到跨进程复用

实际进程映射确认加载 /opt/csa-pto 下的 SDK。
检查进程启动环境未发现 PYPTO_*；SDK 的 _cache_config.py 中，
PYPTO_CACHE 未设置时默认值为 0。结合首批相同核生成 16 份的事实，
当前执行路径表现为各进程分别准备编译产物。

环境检查不等同于排除所有程序内配置覆盖；这里依据的是默认配置与实际重复产物。
多进程并发可能争用 CPU、内存，但没有独占对照，不能定量归因于资源竞争。

### 6.3 预热只覆盖一个图档位，新策略在请求中冷编译

启动脚本配置：

```bash
--max-num-seqs 16
--compilation-config '{"cudagraph_mode": "FULL_DECODE_ONLY", "cudagraph_capture_sizes": [96]}'
```

T=96 与满批 16×6 容量相符，但真实首步、不同 batch、尾批和实际长度组合
可能选择其他编译常量。捕获一个图档位不代表所有业务策略已编译。

动态 shape 与编译期策略是两层机制：

```text
本次输入描述符
  → select_policy
  → 编译期常量组合
  → 本进程缓存命中：直接执行
  → 未命中：生成 IR / C++ / bin，加载后才能继续
```

T、B、页数等是动态维度，同一特化可以复用。
但 QUERY_GROUP、tile 或优化分支等 constexpr 改变，仍可能生成新核。
G2/G6 是核内部资源分组，不是要求实际请求必须有 2/6 个 token，
也不是要求 T 是 2/6 的整数倍。

第 17 套相对启动核的生成代码差异：

| 内部工作区 | 启动核 | 第 17 套 |
|---|---|---|
| coefficients | [T×16,384] | [T×16,128] |
| indexer_transfer | [288,1024] | [96,1024] |
| score_arena | [288,8192] | [96,8192] |

源码按 group×64、24×2×group 计算，明确表明 G6→G2。
第 18 套又是另一种 G6 IR，说明仅分 G2/G6 不能完整标识策略。
尚未取得每次调用的完整 Host 描述符和全部 constexpr，
不把具体 T/B 或某个策略开关当作已确认的逐次触发原因。

### 6.4 请求路径编译阻塞，表现为等待和低吞吐

22:38:48 请求 KV 传输完成后紧接着新编译；
随后出现 “No available shared memory broadcast block found in 60 seconds”。
这种提示是等待，不是 retry，也不能独立证明死锁。
现场编译会延迟 worker 推进；跨 rank 协作可能传播等待，
但没有采集进程栈，不能断言每个 rank 的具体阻塞点。

启动完成后仍发生冷编译，所以 Application startup complete 不等于业务完全热身。
编译影响窗口中的低吞吐不能作为稳定算子性能结论。

## 8. 改进方向（仅建议，未在现场实施）

1. 验证跨进程持久缓存的命中、并发锁和最终二进制复用能力。
   确认 SDK 兼容性、cache key、目录权限以及是否真正省去编译，
   不能只看缓存文件存在，也不能直接复制或重命名 build_output 当作命中。
2. 从业务输入范围整理所需策略，在接流量前预编译/预热。
   同时考虑首步、小 batch、推测 decode、尾批及图外路径；
   不一定要预编译全部 62 档，也不应盲目增加所有图捕获尺寸。
3. 分开验证核缓存与 graph capture。已有核不等于已有适用的图，
   捕获一个图也不等于图外核已准备。
4. 后续增加可审计的启动阶段计时、编译键/策略及 cache hit/miss 记录，
   将编译时间、设备加载、预热、图捕获与稳定执行分开。
   本次未添加日志或改动代码。
5. 对未准备策略的服务行为另行设计并验证；若考虑回退 Native，
   必须保证 cache/state、metadata、图捕获语义一致，不能简单删除门控。

持久缓存可在获准安排的后续启动中评估，例如：

```bash
export PYPTO_CACHE=1
export PYPTO_CACHE_DIR=/path/to/shared/compatible/pypto_cache
```

以上只是配置示意，没有在现场设置；首次未缓存策略依然需要编译。
预编译产物的缓存命中与服务正确性需要实测，不能承诺开启后全部 worker 只编一次。

## 9. 与 ACLNN 工程的关系

本工程历史记录的 62 档是默认选择器枚举的编译策略集合；
每档支持动态维度，编号不是固定 shape。
此次 Python 服务只观察到 6 类 IR，不能据此反推精确 ACLNN key，
也不能把 63 个目录误认为策略数量超过 62。

ACLNN 已预编译核包与 Python JIT 的启动行为不同。
本次分析没有切换服务到 ACLNN，没有调整 tiling/workspace，没有重新验证精度。
详情可结合 [README](README.md)、[动态 shape 说明](DYNAMIC_SHAPES.md)
及 [复现记录](REPRODUCTION.md) 阅读。
